# 2026-08-02 — three fixes in one night, and the only evidence any of them worked was a failing mutant

**An overnight run took three unrelated easy wins, and the same thing decided all three: a green test proves nothing about a test. In two of the three, the version already on `main` passed green over a defect that was really there — including a guard whose own name is `RoundTripsEveryField` reporting success while two fields silently failed to persist.**

The instruction was to take only what could be carried alone, and to skip anything ambiguous rather than ask. That shapes what is worth recording: with no seat to consult, the only way to know a fix was a fix was to break the code on purpose and watch the test notice.

**quince#399, the argv flake, is the clean case.** `TestSpecArgvReachesTheChild` waited for a file to *exist* and then read it, so a read landing inside `os.WriteFile`'s create/write window saw `""`. It had fired on CI for an unrelated PR — the most expensive kind of red, one that belongs to nobody. The fix is two lines. The interesting part is that a passing run after it says nothing at all: the window is microseconds, and the PR that surfaced it had already gone green on a retry over unchanged code. So instead of hunting the race I widened it — `OpenFile(O_CREATE|O_TRUNC)`, `Sleep(300ms)`, `Write` — and ran both wait forms against it. New: 5/5 pass. Old: 5/5 fail, `child argv = ""`, reproducing the CI symptom verbatim. That last line is what closes a diagnosis; five green runs would not have.

**quince#354 is the one worth remembering.** The guard exists to catch a field added to `DeviceIdentityRow` and forgotten in the three SQL enumerations. It skipped every non-string field, and *said so* in an honest comment. I added `Probe int` and `Trusted bool` to the struct, deliberately left them out of the SQL, and the guard on `main` printed `ok`. Two fields not persisting, and the test written to make exactly that impossible reported success. `reflect.Value.String()` is a string-*kind* accessor: on an int it returns the same placeholder for every value, so the comparison was not weak, it was vacuous.

The fix widens the markers per kind — but the part I'd defend is the `default` branch. A kind the guard cannot fill is now a loud failure naming the field, never a skip. That is the same shape as `privacy-check` exiting `2` rather than `0`: a guard that cannot cover something has to say so on the day it is added, because that is the only day anyone can act on it. I mutated that branch too, with a `[]string`, to prove it wasn't dead code — a refusal nobody has ever seen fire is a refusal you are guessing about.

**quince#374 needed the mutation in the other direction.** A WebSocket handshake rejected for an expired session is invisible to script: `onclose(1006)`, identical to a dead daemon. The obvious fix — invalidate the auth query whenever the socket drops — is *worse* than the bug, because `RequireAuth` reads an errored auth status as `needs_login`, so it would bounce a logged-in user to the login screen every time the daemon restarted. The ruling had warned against exactly that trade. So the suite has three negative tests, and a negative test is the easiest kind to write vacuously. I built the naive fix and ran the suite against it: two of the three failed. Without that, "does not report a lost session when the server is unreachable" is a sentence, not a guarantee.

**A gate caught me, too, and it was not the code.** My first PR body said `Fixes quince#399`. `closing-refs-check` refused it: GitHub binds `#N`, `GH-N` and `owner/repo#N`, and a bare repo shorthand is none of them, so the keyword would have parsed, looked right to every reader, and closed nothing — leaving the issue open after its work merged, which reads as a stall and gets the work re-taken. I had written it in the register of someone being precise. Precision that resolves to nothing is the failure this project keeps filing under a different name.

**What I did not do is the other half.** Two candidates were dropped rather than attempted: quince#401, because it touches `storage.zfs.*` keys another runner's live PR is reshaping, and quince#376, because it turns on a UI-shape call nobody had ruled. Skipping is cheap; discovering the collision in review is not.

At the time of writing quince#469 is approved and re-running CI after a rebase, and quince#474 and quince#475 are green and awaiting review. None of the three is merged, and this entry claims nothing about how they land.
